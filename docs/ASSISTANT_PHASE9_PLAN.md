### 3.6 Why these shapes

- A: the stamp is a keyword at the call site, the only place that knows no person is behind the send; a database trigger would hide intent and mislabel deleted-sender rows (9.2).
- B: health rows reuse the whole Phase 8 triage path; the only branch points are a catalog entry, a record-role filter, per-kind decisions, extra `bell_fields` keys and per-kind staleness. Keeping the new facts inside `bell_fields` (a subset-checked dict, `app/assistant/triage.py:667-677`) avoids changing the exact 23-key item contract (`_ITEM_CHECKS`, `:628`) and the 63 golden cases.
- D: a separate kind keeps every Phase 8 self-only pin (`subject_only=True`, `app/assistant/proactive.py:429`; `test_an_escalation_without_a_subject_reaches_nobody`), gets its own mute, label and fuse count, and the router (not an assistant) authors the notice.
- E: a new loop branch beside the browser follow-up, not the Phase 3 `loop.run_unattended` design (`docs/ASSISTANT_PHASE3_PLAN.md:1264-1266`, `:1647`), so the "only `jobs.py` calls `loop.run_turn`" pin (`tests/test_assistant_registry_phase4.py`) holds and the job queue's retry rules apply. The queue's concurrency rules do not apply unchanged: prep turns get their own job type `assistant_triage_prep`, outside `ASSISTANT_JOB_TYPES`, at priority 90 and at most one per process, so a burst waits behind chat by design (5.5). The Phase 3 9.1 toolset controls for an unattended run (`docs/ASSISTANT_PHASE3_PLAN.md:1647`: a run-level read toolset with no memory or schedule namespace, a per-recipe allowlist, `access.owner_check` before the first call) are kept even though the `run_unattended` entry point is not used (`PREP_TOOLS`, 5.5, 6.2); ConfirmRequired cannot arise because `followup_toolset` already drops confirm tools, and a call to any tool not offered is refused with no card (pinned).
